# 📊 Machine Learning - Deposit Decision Prediction: Deploying a Profit Prediction Model as an Interactive Web Application

## I. Context
*   **Overall Objective:** To transition a Machine Learning model from a development environment (Python/Jupyter) into a real-world application, packaged as an interactive Web Application.
*   **Specific Goal:** To construct a user-friendly UI/UX interface enabling stakeholders to input cost variables (R&D, Administration, Marketing) and receive predicted Profit. Additionally, to establish an automated code deployment pipeline to a GitHub repository.
*   **Context / Problem Statement (5W1H):**
    *   **Why is there a problem:** The primary challenge is to democratize access to AI predictions. Without a user-friendly interface, non-technical stakeholders (e.g., Board of Directors, Sales, Marketing teams) are unable to interact with the Python-based Machine Learning model. This creates a technical barrier, preventing them from independently exploring various "cost scenarios" to understand AI-predicted profit outcomes.
    *   **What:** The task involves deploying a web interface (Gradio App) for an existing Multiple Linear Regression model and managing the source code through Git/GitHub.
    *   **Why:** An AI model's true value is realized only when it is applied in practice. If confined to a `.ipynb` file, it remains a set of dormant calculations. The Web App transforms the model into an accessible "Advisory Tool" that can actively inform business decisions.
    *   **How:** The solution involves leveraging the `gradio` library to seamlessly map user inputs from the web interface to the `predict_profit()` function of the underlying model, subsequently displaying the predicted profit output to the user. Finally, shell commands are utilized to push the codebase to the designated `GitHub telesales-analysis` repository for version control and collaboration.
    *   **Where / When:** The development and initial testing are conducted within a Python IDE, which generates a temporary Public URL for the Gradio App, allowing widespread accessibility. This initiative represents the crucial "Deployment" phase within the Data Science project lifecycle, following successful data ingestion, cleaning, Exploratory Data Analysis (EDA), and model training.
*   **Stakeholders & Roles (Who):**
    *   **Data Analyst (You - Quân):** Responsible for designing and implementing the application interface, enforcing robust input data validation, and managing version control and collaboration through GitHub.
    *   **End-users (Management/Investors):** Will interact with the application interface, inputting various data points to generate predictions that inform strategic investment and operational decisions.
    *   **Board of Directors (Strategic Stakeholders):** Will leverage the predictive insights generated by the application to guide strategic resource allocation, evaluate potential business initiatives, and make high-level decisions regarding company growth and direction.

## II. Domain Knowledge & Terminology
*   **Multiple Linear Regression:** A statistical technique that uses several explanatory variables to predict the outcome of a response variable. In this project, it's used to model the relationship between cost variables (R&D, Administration, Marketing) and Profit.
*   **Gradio:** An open-source Python library that simplifies the creation of customizable user interfaces for machine learning models. It enables quick deployment and sharing of models as interactive web links, making them accessible to non-technical users.
*   **Model Deployment:** The process of integrating a trained machine learning model into an existing production environment or an application, making its predictions available for real-time use by end-users or other systems.
*   **UI/UX (User Interface/User Experience):** UI refers to the visual elements and interactive properties of an application. UX focuses on the overall experience a user has when interacting with the application, emphasizing ease of use, efficiency, and satisfaction.

### 2. Data Dictionary
The following columns are expected as inputs for the model and the output received from its prediction.

| **Column Name** | **Description** | **Data Type** | **Encoding / Notes** |
| :---------------- | :---------------------------------------------- | :------------ | :------------------------------------------------------------------------------------------------- |
| `age` | Customer's age | `Integer` | Check for outliers (too old/too young). Use for age binning. |
| `job` | Customer's occupation | `String (Category)` | Includes: admin, technician, management, retired, unemployed... Need to handle 'unknown' values (Use One-hot encoding for ML). |
| `marital` | Marital status | `String (Category)` | Includes: married, single, divorced (divorced includes widowed). |
| `education` | Education level | `String (Category)` | Includes: primary, secondary, tertiary, unknown. Ordinal data, consider Label Encoding. |
| `default` | Has credit in default? | `String (Boolean)` | `yes` = Defaulted, `no` = No default. Data is usually highly imbalanced. |
| `balance` | Average yearly balance (Euro) | `Integer` | Can be negative (overdraft). Needs scaling (Standard/MinMax) for ML models. |
| `housing` | Has housing loan? | `String (Boolean)` | `yes` = Has loan, `no` = No loan. |
| `loan` | Has personal loan? | `String (Boolean)` | `yes` = Has loan, `no` = No loan. |
| `contact` | Contact communication type | `String (Category)` | Includes: cellular, telephone, unknown. |
| `day` | Last contact day of the month | `Integer` | 1 to 31. Should be combined with the `month` column to create a Date format for Time-series analysis. |
| `month` | Last contact month of year | `String (Category)` | Includes: jan, feb, mar... dec. Seasonality might affect deposit decisions. |
| `duration` | Last contact duration (seconds) | `Integer` | **CRITICAL NOTE:** This variable directly affects the Target (duration=0 means deposit='no'). Causes **Data Leakage**. Must be *dropped* when building the predictive model. |
| `campaign` | Number of contacts during this campaign | `Integer` | Includes last contact. Measures contact intensity (1 and above). |
| `pdays` | Days passed since last contacted from a previous campaign | `Integer` | Convention: **-1** means the client was *not previously contacted*. Be careful when calculating Mean/Median as -1 adds noise. |
| `previous` | Number of contacts performed before this campaign | `Integer` | 0 and above. Represents customer interaction history. |
| `poutcome` | Outcome of the previous marketing campaign | `String (Category)` | Includes: unknown, other, failure, success. Past 'success' often correlates with current 'success'. |
| `deposit` | Has the client subscribed to a term deposit? | `String (Boolean)` | **Target Variable / Label.** `yes` = Subscribed, `no` = Not subscribed. Need to map to 1 and 0 for Binary Classification. |
